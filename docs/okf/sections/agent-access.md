# Agent access (MCP)

Source of truth: `docs/sections/agent-access/` in the repository. This concept is generated by `scripts/build-okf.mjs`; edit the source files, then run `npm run okf:build`. Relative links inside the embedded text point at repository paths, not bundle concepts.

## Behavior and code map

Automator runs a Model Context Protocol server inside the Electron host so Claude Code (or any MCP client) can use scripts, browser automations and Work Time without anyone starting a separate service. The server starts with the app, stops when the app quits, and listens on `127.0.0.1` only.

### Connecting Claude

Open **Settings → Agent access (MCP)**, check that the status reads *Listening*, press **Copy Claude command** and run it in a terminal:

```
claude mcp add --transport http automator http://127.0.0.1:47821/mcp --header "Authorization: Bearer <token>"
```

The command is built and copied by the host. The token is never shown in or sent to the renderer.

### Settings

- **Let Claude use Automator** turns the server on or off. It is on by default and the choice persists across launches.
- **Port** defaults to 47821. If the port is busy or reserved by Windows the status says so and the server stays off until another port is chosen. Automator never picks a different port silently, because Claude's saved URL would break.
- **Regenerate token** (two-step confirmation) invalidates the old token immediately. Agents must be registered again with a newly copied command.
- Configuration lives in `mcp.json` beside the host's local data (`%LOCALAPPDATA%\Automator`, or the isolated test directory). The token is encrypted with Electron `safeStorage` (Windows DPAPI). It is not part of the settings backup.

### Tools

| Tool | Purpose |
|---|---|
| `list_scripts`, `get_script` | Saved Script Runner profiles marked **AI can use**, with their typed inputs (type, required, hint, example, options, defaults). |
| `run_script` | Runs a script with typed `values`. Returns the result inline, or a `runId` if it takes longer than `waitSeconds` (default 20, max 60). |
| `get_run`, `list_runs`, `cancel_run` | Poll, list and cancel runs started through MCP. |
| `list_browser_automations` | Browser profiles (start URL, allowed hosts) and, with `includeTests`, discoverable Playwright tests. |
| `run_browser_automation` | One action in a browser profile (`target: profile`) or Playwright tests (`target: tests`, kind `test`, `file` or `tag`). Async like `run_script`. |
| `get_running_timers` | The running Work Time timer (at most one), paused timers and the count of unsaved drafts. |
| `register_time` | Adds a finished entry for `hours`/`minutes` ending now (or at `endedAt`), with description and tags. |

Scripts are opt-in: each script has an **AI can use** checkbox in the Script Runner editor (saved as `aiAccess` on the profile, off for new and existing scripts). `list_scripts` omits unchecked scripts, and `get_script` and `run_script` answer with the same "No script with id" error as for a missing script, so the filter is enforced in the MCP layer (`electron/mcp/tools.ts`), not only in the UI. Browser profiles work the same way: a checkbox per profile in the Browser Automation tab (`aiAccess` on the profile, off by default) controls `list_browser_automations` and `run_browser_automation` with `target: profile`. Playwright tests (`target: tests`) are not profile-bound and stay available. The agent's own per-tool permission prompt is the confirmation step, so keep `run_script` and `run_browser_automation` on "ask" in Claude Code.

### How it works

`electron/mcp/server.ts` is a small stateless Streamable-HTTP MCP implementation (`initialize`, `ping`, `tools/list`, `tools/call`; responses are plain JSON). Each request is checked in order: `Host` must be `127.0.0.1:<port>` or `localhost:<port>` (DNS-rebinding guard), a present `Origin` must be loopback, and `Authorization: Bearer` must match the token (constant-time compare). Bodies are capped at 256 KiB and tool results at 200,000 characters.

Tools call the backend through `electron/mcp/backendBridge.ts`, which sends the normal `automation/moduleAction` RPC with a host-built `hostWindowContext` of `{role: 'workspace', selectedTab: <slot>}`. The slot, contract version and action versions come from the live tab registry. Because the host builds the context, an MCP client can reach a module even when its tab is not selected, and can never supply its own context.

The backend blocks for the length of a run, so `electron/mcp/runRegistry.ts` keeps the call open and records the outcome in memory: the newest 50 runs, at most 4 running at once, request ids prefixed `mcp-`. Cancelling uses `automation/moduleActionCancel`. Output is never persisted or logged. Run Activity still records metadata for each run through the backend. Quitting the app cancels running runs before the backend stops.

## Contributor rules

Read the root AGENTS.md first. This surface lets an external agent run real actions on the user's computer, so treat every change as a security change.

- The server must stay bound to `127.0.0.1`. Do not add `0.0.0.0`, an IPv6 wildcard or LAN binding, and do not weaken the Host, Origin or bearer-token checks in `checkRequestAccess`. Keep the token comparison constant-time.
- The bearer token must never reach the renderer, logs, run output, backups or error text. The host builds and copies the Claude command itself. Do not add a renderer API that returns the token.
- `hostWindowContext` is always built by `backendBridge.ts`. Never accept a context, slot or module id from the MCP client beyond the fixed tool-to-module mapping, and never add a tool that forwards an arbitrary module action.
- Do not add tools for arbitrary shell, arbitrary JavaScript, or editing/deleting scripts, profiles or credentials without an explicit product decision. Browser actions must remain bounded by each profile's allowed hosts.
- Log only tool names and status (`Mcp.ToolCall`). Never log arguments, script values, stdout/stderr or page text. Unexpected errors return a generic message; only `McpToolError` and backend RPC messages are shown to the agent.
- Script tools must go through `aiScripts()` so only profiles with `aiAccess === true` are listed, described or run. Browser profile tools do the same with `aiBrowserProfiles()` / the `aiAccess` filter. Never add a script or profile tool that reads profiles without that filter; missing and unshared scripts must be indistinguishable.
- Script output and web text returned to the agent are untrusted. Keep the warning in the tool descriptions.
- Keep run output in memory only (`RunRegistry`). Preserve the 50-run and 4-concurrent limits and cancel running runs on quit and when the server is switched off.
- Keep a stable default port (`MCP_DEFAULT_PORT`); never fall back to another port silently. Test mode uses an ephemeral port and the isolated data directory, so tests must not use fixed ports or touch `%LOCALAPPDATA%\Automator`.
- New tools need a zod input schema, correct `readOnlyHint`/`destructiveHint` annotations, a case in `tests/mcp-server.test.mjs`, and a row in the README table. Tool names are snake_case and part of a public contract.
- Work Time tools reuse the `focus-sessions` actions and their validation. If the Work Time contract changes, update `register_time` and `get_running_timers` and their tests in the same change.
- Update this README, the Settings text in `ui/AgentAccessSettings.tsx`, and the script-runner, browser-automation and work-time docs when tool behavior changes.
