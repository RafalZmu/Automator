# Browser Automation — slot 4

Source of truth: `docs/tabs/browser-automation/` in the repository. This concept is generated by `scripts/build-okf.mjs`; edit the source files, then run `npm run okf:build`. Relative links inside the embedded text point at repository paths, not bundle concepts.

## Behavior and code map

The tab has two related surfaces:

- **Playwright Test Explorer** discovers tests in the managed project or a selected existing Playwright project. Sections are test files; Automator-managed tags can group tests across files. Run one test, all tests in a section, or a tag group and inspect combined outcomes.
- **Browser profiles** use an Automator-managed isolated browser session for saved navigation and interaction actions. A profile stores its start URL and host grant.

When the configured managed project is first created, Automator creates a tests directory and an example spec file. For an existing project, choose its project root; Automator does not install or change that project's dependencies.

While editing a test's tags, tags already used on any test in the project are offered as clickable suggestions under the input (filtered by what you are typing; picking one adds it to the comma-separated list). The code button on each test row loads that test's source (from its declaration line to its closing bracket, at most 200 lines) from the host through `readTestSource` and shows it inline; select it again to hide it. The view is read-only.

Runs started from the Playwright Test Explorer are listed in Run Activity without a saved profile identifier.

### Running state and run history

A run belongs to the window, not to the Browser Automation view. Start a test, section or tag group (from the tab or from the compact window's action search), close the window and reopen it: the run keeps going, a **Running** banner with elapsed time and Cancel appears at the top of the tab, and a pill with the target shows in the header on every screen (click it to jump back). The backend starts these runs outside the compact window's shared context, so hiding the window or changing tabs does not cancel them (Cancel, quitting Automator and the timeout still do). Tests are discovered when the tab opens for any selected project, and **Run history** is always shown, with an empty-state line until the first run. Only one run is active per window; a run started by another window or an agent shows as running too (without Cancel) until it ends.

Every finished run is saved to the Automator library database (`browser-automation/run-history`): target, kind, state (Passed, Failed, Timed out, Canceled, Error), start time, duration, exit code, a count of passed, flaky, failed, timed-out, skipped and interrupted tests, and up to 256 per-test outcomes. The newest 200 are kept across restarts. **Run history** is hidden by default. In the compact window it opens as a panel on the left: the window widens to the left by the panel width (about 220 ms ease, clamped to the screen's work area) so the existing content stays where it was, and narrows again when the panel is closed or you leave the tab. In the workspace window it stays an expandable section at the bottom of the tab. Whether it is open is remembered on this computer. Each entry shows its counts, such as `2 passed · 1 failed · 2 timed out`. Select an entry to open its results, or use **Clear history**.

In a run's results, tests that did not pass are listed first, each with its status, its file and failing line, the step that failed (for example `expect.toBeVisible` or `locator.click`), its attempt count, and a reason:

- **Test timed out**: the whole test passed its time limit.
- **Hook or fixture timed out**: a `beforeEach`, `beforeAll`, or fixture passed its time limit.
- **Expect timed out**: a retrying expect (such as `toBeVisible`, `toHaveText`, or `expect.poll`) kept failing until its timeout.
- **Expect failed**: an expect compared a value that did not match.
- **Action timed out**: a page action, such as a click, waited past its timeout.
- **Runner limit reached**: Automator stopped the run at its time limit while this test was still running.
- **Error** or **Interrupted**: any other failure, or a run that ended before the test finished.

A test that passed only after a failed attempt is **Flaky**, and its error is from the attempt that failed. Passed and skipped tests are collapsed under one line. The error text is shown first; the code around the failure is one click away. Reasons and steps come from the run events that Automator's Playwright reporter writes; when those are unavailable, the reasons come from Playwright's JSON report, which carries less detail. The stored error excerpt is 500 characters and the code excerpt 900. They may contain values from the page or your test. Raw runner output is never stored. Run Activity keeps its own metadata-only entry for each run.

The Codex task builder can create a generated Playwright task in the configured Automator-managed project's `tests/codex` folder. It saves a `playwright-task` profile with the managed project identity, relative spec path, named JSON inputs, declared scope/effects, and approval revision. Workflows can call this profile and map JSON values into its inputs. A changed source, scope, or declared effects must be reviewed and reapproved before execution. Generated test code runs with the signed-in Windows user's permissions; the displayed scope is consent context, not a sandbox. Existing selected projects and their dependencies are not rewritten by this feature. See [Codex](../codex/README.md) for generation and approval details.

## Contributor rules

Read the root AGENTS.md first. This tab contains both saved browser-action profiles and the Playwright Test Explorer.

### Playwright test authoring and maintenance

- Keep discovery, metadata, file creation, tag persistence, and test invocation host-owned in PlaywrightTestExplorer.cs; the renderer only dispatches validated module actions.
- The managed project is selected/configured by the host and is seeded with tests/example.spec.ts. Do not make an arbitrary test-folder path a mandatory user setting. Users may select an existing Playwright project.
- Each Explorer section is a Playwright test file. Add tests using the project's installed @playwright/test APIs and conventional .spec.ts, .test.ts, .spec.js, or .test.js files that the discovery implementation accepts.
- Do not install, upgrade, or rewrite dependencies in a user-selected project. If its Playwright runner is missing, show the existing setup error and let the user/agent maintain that project explicitly.
- Store Automator-managed tags as metadata keyed to the test/project identity; do not modify test source to add tags. Keep stale-tag cleanup explicit.
- Preserve the project-root containment and reparse-point checks when creating or editing section files.
- `readTestSource` is read-only: it resolves the test through discovery by id, keeps the project-root containment and reparse-point checks, caps the file at 2 MiB and the returned excerpt at 200 lines. Discovered file names come from `playwright test --list`, which prints them relative to the configured `testDir`, so the host may need to locate the file under the project root (bounded breadth-first search, no reparse points, skipping `node_modules` and `.git`). Tag suggestions are derived in the renderer from the explorer's known tags; do not add a separate suggestion store.
- Run individual tests, a section file, or a tag group through the host process service. Never build a shell command by concatenating project paths or test names.
- Playwright test runs have no saved profile and are recorded in Run Activity with a null profile ID; keep that field explicit in the activity RPC response.
- Codex-generated Playwright tasks are stored as `playwright-task` profiles under the managed project's `tests/codex` directory. Keep their relative paths contained in that project, preserve create-new behavior, validate their declared JSON inputs, and reject a source hash that no longer matches its approval. They run through this host-owned Explorer path; do not rewrite tests in a user-selected project or change project dependencies.
- Generated-task scope is displayed for review and consent, not enforced as an OS boundary. A changed saved source or declared scope/effects requires review and reapproval before a Workflow invokes it.
- Start Playwright runs through `startBrowserRun` in `ui/modules/browserRunStore.ts` and dispatch through the bridge, not the per-tab `services` object: `services` is disposed when the active tab changes and the view unmounts when the compact window reopens on its home surface. Never abort a run in an unmount cleanup.
- `runTests` (and Script Runner `runProfile`/`runAgain`) are "detached" in `BackendServer.IsDetachedRunAction`: they get their own module-services context and register with `survivesModuleCancel`, so `DeactivateServicesAsync` (panel hidden or tab changed) does not cancel them. Keep new long-running run actions on that list.
- Run history is host-owned. `PlaywrightTestExplorer.RunAsync` saves one `run-history` record per run (success, failed, timed out, canceled, error) after the process ends, bounded to 200 and 256 outcomes, and keeps an in-memory active-run list for `listRunHistory`. Persistence is best effort and must never change the run result. Store titles, files, lines, statuses, attempt counts, the failing step and line, a classified failure `reason`, one ANSI-stripped error excerpt of at most 500 characters and one code excerpt of at most 900 characters per failed test; never stdout/stderr, traces, screenshots or page content.
- Per-test outcomes come from the run events that `src/Automator.Infrastructure/Automation/playwright-run-reporter.cjs` writes. The host passes it with `--reporter=json,<path>` and points it at a temp `AUTOMATOR_PLAYWRIGHT_RUN_EVENTS` file that is deleted after the run. The reporter must never write to stdout, which carries the JSON report, and each event line is a `begin` or `end` record keyed by Playwright's test id, so a runner-limit stop can name the test still running. Playwright's JSON report only covers runs without the reporter: it omits expect and action steps, so it cannot name the failing step. The reporter path is set by `electron/main.ts` (packaged, next to `browser-worker.cjs`) and `scripts/dev.mjs` as `AUTOMATOR_PLAYWRIGHT_RUN_REPORTER_PATH`, and `scripts/package-win.mjs` copies it and records it in the build manifest.
- Classify reasons from structured fields first (the failing step's category and Playwright's timeout markers such as `Timeout 5000ms` or `Test timeout of … exceeded`), never from the bare word "timed out", which can appear in a received value. Keep the stored reason values stable: older records must keep their labels.
- Browser-action profiles must continue using the isolated host browser session and their saved host grant. Do not introduce unbounded navigation or bypass host network policy.

### Run history side panel

- In the compact window the history is a left panel and the host resizes the window; the renderer must never move content to fake it. Content keeps its screen position because the shell's left padding grows with `100vw - 760px` and the panel slot fills that strip, so `760` in `ui/styles.css` must match `panelSize.width` in `electron/main.ts`, and the panel's `300px` must match `SIDE_PANEL_WIDTH` in `electron/platform.ts`.
- Keep the width/position math pure in `electron/platform.ts`. A hidden window only records the open state; `placeNearPointer` sizes it when it is shown. Only the launcher role is resized (`automator:set-side-panel`); the workspace window and the browser preview keep the inline section.

### Browser profile and explorer contracts — tests/browser-automation-contract.test.mjs

#### browser profile validation requires its start host in an exact allowlist

**Steps**

1. Validate a profile whose start URL host matches an exact host allowlist.
2. Change the URL to a host outside that allowlist and validate again.

**Expected result:** A matching host is accepted; an unlisted start host is rejected.

#### browser actions reject unsupported, oversized, malformed, and out-of-policy inputs

**Steps**

1. Validate a supported browser action and its input.
2. Repeat with an unsupported action, malformed parameters, oversized values, and a URL outside the saved host policy.

**Expected result:** Only bounded, well-formed actions allowed by the saved host policy are accepted.

#### browser result decoding accepts bounded known fields and ignores malformed links

**Steps**

1. Decode a result containing a URL, title, text, and both valid and malformed links.
2. Provide an oversized current URL and a malformed profile record.

**Expected result:** Known bounded fields and valid links are retained; malformed links, oversized results, and invalid profiles are ignored or rejected safely.

#### Playwright list parsing groups exact project, file, location, and title identities

**Steps**

1. Parse a Playwright list containing the same test under Chromium and Firefox projects plus a second test file.
2. Inspect project, file, line, nested title path, list entry, and generated identity.

**Expected result:** Each project/file/location/title combination is parsed, and the same test under two projects receives distinct identities.

#### Playwright section path validation allows test files under the project and rejects traversal

**Steps**

1. Validate a project-relative spec path.
2. Try parent-directory traversal, a text file, an absolute path, and an unsupported test extension.

**Expected result:** A supported in-project test path is returned; traversal and unsupported paths are rejected.
