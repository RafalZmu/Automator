# Script Runner — slot 2

Source of truth: `docs/tabs/script-runner/` in the repository. This concept is generated by `scripts/build-okf.mjs`; edit the source files, then run `npm run okf:build`. Relative links inside the embedded text point at repository paths, not bundle concepts.

## Behavior and code map

Script Runner saves reusable Python, Bash, and PowerShell scripts as profiles. A profile has an interpreter path, script path, optional fixed arguments, working directory, output mode, timeout, and an ordered list of typed inputs.

Inputs are declared in the profile editor (Inputs section) with a label, a type (Text, File, Folder, Yes or no, or Choice), an optional default, Required, an optional hint, and an optional example. The hint appears next to the label in the Run form; the example appears as faint placeholder text in the empty box and is never submitted. Bundled templates declare hints and examples for their inputs too. Each input becomes one argument, in list order, after the fixed arguments. Running a script with inputs opens a Run form that uses the same typed fields as the Library. Remember these values stores the non-sensitive values on the profile, so the next Run form and Workflow or Scheduler runs use them. Passwords are never remembered. Scripts without inputs run directly from their row. The interpreter path can be remembered as a default for new profiles; changing that default does not silently rewrite existing profile paths.

Run and Edit open inside the script's own row: pressing **Run** on a script with inputs, or **Edit**, expands the form under that row so the two stay visibly connected, and pressing the same button again closes it. Only one form is open at a time, so opening Edit closes Run and the reverse. A new script, and the draft opened by **Register in Automator**, have no row yet and open at the top of the list.

Each argument row is passed as one process argument, including values containing spaces. Text mode displays bounded stdout and stderr. JSON mode parses stdout as one JSON value and displays it as structured data. Scripts run as the signed-in Windows user and are not sandboxed.

The Codex task builder can save a successfully run Python task as a normal Script Runner profile. Codex approval metadata ties the saved task to the reviewed source and scope; changed task source or declared review details must be reviewed and reapproved before manual, Workflow, or Scheduler execution. Scope is consent context and does not limit the script's Windows-user permissions. See [Codex](../codex/README.md) for the authoring and review flow.

### Script Library templates

The Script Runner Library provides registered bundled templates that can be installed as ordinary profiles. Each template card has a primary `Add to Script Runner` action beside `Details`; after installation, the card shows `Profile added`. Open `Details` on a template that is not installed to review its inputs and add it with the values you entered. For an installed template, `Details` opens the same Run form as its profile row. Firebird 3 templates keep their `Target database` path field visible on the Library card before Details or installation, so you can choose the database while adding the template. The field value stays transient for the template run and is not saved in the profile. Other template inputs appear in the Details form; both Firebird templates default to `SYSDBA` / `masterkey`, and each password is transient and is not saved with the profile. Template runs require the Script Runner form. Workflow or Scheduler attempts to run a template profile do not have transient credentials and fail with a message to run it interactively. Editing a library profile changes only its name and shows its inputs read-only. Make an editable copy turns it into your own script with the same inputs; templates with a password cannot be copied, because passwords are never saved.

File and directory fields accept a pasted or typed path, Browse, or one dropped filesystem item. Dropped items resolve to a local path; Automator does not read their contents. File and directory inputs require fully qualified paths; output destinations need not exist yet. The Firebird `gbak` executable and ZIP destinations are entered as paths in the template form. The password stays out of saved profiles, settings, and logs. During execution the local process command line may expose the credentials to other processes running as the same user; this visibility is accepted for the initial template.

An installed template card also has **Add another copy**. Each copy is a separate profile that shares the one installed script, named like `Archive stale .fdb databases (2)`. Its editor opens right away so you can rename it and set its own values (for example a different source folder), then use **Remember these values**. This lets one library script run against several folders without editing the script. Each copy has its own Explorer mappings, Workflow and Scheduler entries, and run history. Removing a profile never removes the shared script.

Templates are bundled trusted code and run unsandboxed with the same Windows-user access as Automator. Review a template and trust its source before running it. The shared path field is currently reused in Script Runner only; other tabs can adopt it in a later focused change with their own authorization and docs.

The Library also includes **Archive stale .fdb databases**. Set a source folder and a number of days. Each `.fdb` under the folder (and its subfolders, unless Include subfolders is turned off) that has not been accessed for that many days is zipped beside it as `<name>.fdb.zip`, or as `<name>.fdb.<yyyyMMdd_HHmmss>.zip` when that name is already taken. The archive is checked against the original by SHA-256 before the original is deleted. Locked files are skipped and reported. **Preview only** is on by default and changes nothing; turn it off in the form to archive. Template profiles run only from the Script Runner form, so Scheduler and Workflows cannot run this template. For unattended runs use `scripts/Backup-StaleFdb.ps1` with Task Scheduler. Last access times are only meaningful when NTFS last access updates are enabled.

The Library also includes **Update Automator and restart**. Set **Automator checkout** to the git folder Automator was built from (for example `C:\Automator`). The run first checks that git, `node.exe`, `npm.cmd`, and `dotnet.exe` are on PATH, then runs `git pull --ff-only --no-rebase` in that folder and prints the new commits. `--no-rebase` keeps a `pull.rebase` git setting from rebasing local commits or refusing every uncommitted file, so only edits to files that the incoming changes also touch block the pull. If the pull fails (a diverged branch, no upstream, such an overlapping edit, no network), the run fails with git's message and Automator keeps running. If nothing new was pulled the run stops there too, unless **Rebuild even if nothing new was pulled** is on.

Otherwise the run starts a background worker and finishes. A few seconds later the worker stops the checkout's Automator processes, runs `npm ci` when `package.json` or `package-lock.json` changed since the last install (the same stamp as `scripts/Build-And-Run-Automator.ps1`), installs Electron's Windows runtime when `node_modules\electron\dist` is missing (npm can skip Electron's install script), runs `npm run package:win`, and starts the packaged app with `scripts/Restart-Automator.ps1 -Show`. Run history therefore shows only the pull. The build log is `artifacts\update-and-restart\update-<time>.log` in the checkout; the newest ten are kept. If a step fails, the worker writes the error to the log, tries to start the app again, and shows an error message box that says whether it did. A failure before packaging starts (dependencies, type check, compile, backend publish) leaves the previous build, so Automator comes back on it. Packaging clears the previous build first, so a failure during packaging leaves nothing to start and Automator stays closed until you fix the problem and run this again or run `npm.cmd run package:win` yourself. Uncommitted edits in the checkout are included in the build. This updates the packaged `win-unpacked` app of that checkout, not a development host or a portable copy.

### Creating scripts that work well here

- Use .py with the configured Python executable, .sh with a configured Bash executable such as Git Bash, and .ps1 with PowerShell.
- Put every argument on its own line in the profile. Do not include shell quotes just to preserve spaces; Automator passes each line as one argument.
- Set the working directory explicitly if the script reads or writes relative paths.
- Keep stdout clean in JSON mode: emit one JSON document and send diagnostics to stderr. In text mode, stdout and stderr are shown separately.
- Validate arguments, avoid interactive prompts, return a meaningful nonzero exit code on failure, and keep expected runtime within the profile timeout.
- Treat scripts as trusted code with the same access as Automator. Never place credentials in source files, arguments, output, or logs.

### Running state and run history

A run belongs to the window, not to the Script Runner view. Start a script from the compact window's action search, close the window, and reopen it: the script keeps running, a **Running** banner with elapsed time and Cancel appears at the top of Script Runner, and a pill with the script name shows in the header on every screen (click it to jump to Script Runner). Only one script runs at a time.

Finished runs appear in **Run history** below the result: status (Succeeded, Failed, Timed out, Canceled, Error), start time, and duration, newest first, up to 30. A failed, timed-out, or errored run also shows a one-line reason under its row: the first line of the script's error output, or the run message when there is none. Select an entry to read its output as a past result; **Clear history** removes finished entries. File Explorer action runs are tracked the same way (running banner, header pill, history) and keep running when the compact window closes. History and output are memory-only in the window that ran the script and are cleared when Automator restarts; the Run activity list keeps permanent metadata without output. The compact launcher and the Workspace window each keep their own history.

### Removing profiles

The Remove button on a profile row uses a two-step inline confirmation: the first click shows Yes and Cancel, Escape or Cancel dismisses them, and they reset after six seconds. The command-palette delete keeps its own confirmation prompt.

### File Explorer actions

Open **Explorer actions** in Script Runner and press **Add action**. Choose a saved profile, enter the menu label and extensions (for example `.fdb, .txt`), then save. Extensions are normalized and duplicate entries are removed. For a regular script, put `{{file.path}}` in its saved arguments first. For an installed Library template, choose which file or directory parameter receives the selection.

In the stable Windows package, right-click a matching file in File Explorer and choose **Automator → your action**. Windows 11 may place the submenu under **Show more options**. The app opens Script Runner with a review form and the selected file prefilled, including paths with spaces and Unicode. Press **Run** to execute or **Cancel** to dismiss it. Regular arguments can be edited for that one run. Template forms list every input of the script in order, with example text and hints; the input the mapping points at shows the selected file read-only, and remembered values from the saved profile prefill the rest. Credentials stay transient. Neither is saved to the profile. The backend checks the selected existing absolute file and extension again when Run is pressed.

Mappings can be edited or removed individually. **Remove all Explorer actions** clears the mappings and owned menu entries; deleting a saved profile removes its mappings. A registration error leaves the saved mappings visible; reopen the section to retry. Registration is disabled in development, portable, and test-mode hosts. Automator only writes its owned per-user menu keys and never changes the default file association.

In the stable Windows package, the `.ps1` **Automator** submenu also contains **Register in Automator**, even when no run actions are mapped. It opens a new PowerShell profile draft with the script path, filename-based name, and containing folder filled in. Review the interpreter and other fields, then choose **Save profile** to add it to Script Runner; the script is not run by registration or saving. Cancel leaves the Library unchanged.

The Library includes **Firebird 3 database backup** and **Firebird 3 database backup and ZIP**. Install either template and map it yourself; neither action is enabled automatically. Both offer the target database on the Library card, with backup destinations, `gbak`, username, and password in their typed run forms. For the target-database input the Library card and Explorer form ask for the `.fdb` file. **Backup file** is optional: when empty it is saved beside the `.fdb` with the same name and an `.fbk` extension. In the ZIP template **ZIP file** is optional too and defaults to the same name with `.zip`. These defaults are computed by Automator before the script starts, not by the script. V1 handles one selected file at a time. The Library also includes **Firebird 3 database restore**, the matching restore: it runs `gbak -c` on the backup into a temporary file beside the target and moves it into place only after `gbak` succeeds. It never overwrites an existing database unless **Replace existing database** is on, and even then a failed restore leaves the existing database untouched. It fails with a clear message when the backup is missing or empty or the target folder is not writable. **Backup file** defaults to the `.fbk` beside the `.fdb`.

Explorer action UI lives in `ui/modules/ExplorerActionsPanel.tsx`; `explorerActionViewModel.ts` prepares transient forms. The mapping form preselects the template's first file or directory input for the selected file, which is the database for the Firebird templates; choose the input that takes the file itself, not an output path. Explorer runs start through `startScriptRun` in `scriptRunStore.ts`. `ui/App.tsx` retains typed preload launch requests before the Script Runner view mounts. `ScriptRunnerExplorerActions.cs` stores and validates mappings/runs, while the Windows capability reconciles the classic cascading menu.

## Contributor rules

Read the root AGENTS.md first. Script Runner executes saved, trusted user scripts as the current Windows user. It is not a sandbox.

### Adding a profile or script capability

- Keep profile validation and execution in `src/Automator.Application/Automation/ScriptRunnerModule.cs` and `ScriptRunnerSavedProfileHandler.cs`; renderer code must call the module through AutomationServices.
- Preserve structured process arguments. The UI stores one argument per line, and each line is one argument value. Never build a shell command by concatenating profile fields.
- Run and Edit forms render inside the profile's own row (`script-profile-item`). The editor stays attached to its row through `editingOriginalId`, because the profile key is editable while editing; a new or PowerShell-registration draft has no row and renders at the top. Edit and Run are mutually exclusive.
- Declared inputs (`parameters`) use the same typed model as template parameters (`ScriptRunnerParameters.cs`). Argument order is fixed arguments first, then inputs in list order. Template profiles take inputs from the catalog and must not store their own `parameters`. `example` is display-only placeholder text (max 256 characters); never use it as a value or default.
- Remembered `values` are non-sensitive only. `saveProfile` rejects sensitive keys; the Run form, Library form, and Workflow/Scheduler runs read values through `ScriptRunnerExecution.BuildArguments`. Required inputs are enforced when running and may be empty while saving.
- Declared inputs are part of the Codex approval revision (`HashProfileRevision`). Profiles without inputs keep their existing hash.
- The accepted interpreter/script pairs are Python with .py, Bash with .sh, and PowerShell with .ps1. PowerShell is invoked non-interactively with -NoProfile; Bash should use the configured executable, such as Git Bash.
- Interpreter defaults apply when creating or changing a profile. A saved profile retains its own interpreter path. All paths are absolute; working directory, per-argument limits, and the 1–3600 second timeout are validated.
- Script processes must not require interactive prompts. Exit code zero means success; nonzero exits and timeouts must remain visible as failures/warnings. Keep stdout/stderr bounded.
- For JSON output mode, stdout must contain exactly one valid JSON document. Send progress and diagnostics to stderr so they do not corrupt JSON parsing.
- Global variable references in argument values use the form {{variables.name}}. Do not interpolate arbitrary environment variables or commands.
- Do not put secrets, script output, or response data in application logs. Do not automatically execute follow-up actions from script-provided data; actions must be declared and validated by the Automator module and require a user click.
- Bundled template origins are valid only for the exact registered version, installed script path, and embedded asset bytes. Do not preserve template origin when converting a library profile into an ordinary edited script.
- Firebird template credentials are transient form values and must never be saved to profile arguments. Template profiles require an interactive Script Runner run; Workflow/Scheduler saved-profile calls have no transient inputs and must fail clearly without starting the script.
- Codex-generated Python is saved as an ordinary Script Runner profile and uses the same structured process runner. Preserve its optional Codex approval metadata when editing unrelated profile fields; changed source or declared review scope requires review and reapproval before manual, workflow, or scheduled execution. The Codex scope describes consent and does not sandbox the generated script.
- Registry writes from a packaged host (for example the Claude desktop app) are redirected to a private copy that Explorer never reads. Start Automator from Explorer or the Start menu, not from such a host, when checking Explorer menu registration.
- Keep the Firebird `Target database` path field visible on its Library card before Details or installation; carry its value as a transient template input and never add it to saved profile arguments.
- `installTemplate` accepts `copy: true` to add another profile for an already-installed template. The copy reuses the installed script only when it still matches the bundled asset byte for byte; otherwise the install fails and asks for repair. Copies are named `<template name> (n)` using the first free number. Never delete the shared script when a profile is removed.
- Keep a distinct primary `Add to Script Runner` action directly on every Library template card beside Details. Show `Profile added` for an installed template; Details must still open its interactive form for that saved profile.
- Catalog parameters may set `DefaultFromKey` and `DefaultFromExtension` (both `JsonIgnore`, so they never reach the renderer or user profiles). `ScriptRunnerParameters.Resolve` fills an empty value with the other input's path and the given extension. Use this instead of editing a shipped template script: the installed copy must match the embedded asset byte for byte (`MatchesInstalledAsset`), so a changed script needs a new template version and a migration for existing profiles.
- File and directory template inputs must be fully qualified paths, but may name output paths that do not exist yet.
- `update-and-restart` stops Automator, which also ends the script that runs it, so its rebuild runs in a second copy of the same script (`-Worker`, plus internal `-WaitForProcessId`, `-LogPath`, `-ToolDirectories`, `-NoDialog` that Script Runner never passes). The foreground part pulls first (`--ff-only --no-rebase`, no credential prompts; without `--no-rebase` a `pull.rebase` git setting turns the pull into a rebase that refuses any uncommitted file) and must finish every check that can fail before the worker starts, because the worker stops the app. Start the worker with `Win32_Process.Create`, not `Start-Process`: that keeps it outside the host's process tree (which `Restart-Automator.ps1` and cancel/timeout kill) and gives it none of the run's redirected output handles, which would keep the run open. A WMI process gets the user's default environment, so tool directories are passed explicitly. The worker must try to restart the app after a failed step, log to `artifacts\update-and-restart`, and tell the user in the log and the dialog whether the app was restarted: `scripts/package-win.mjs` deletes `artifacts\electron-dist` just before electron-builder runs, so a failure while packaging leaves no build to start and the app stays closed. Do not claim otherwise. Build steps must stay the documented ones (`Restart-Automator.ps1`, `npm ci`, the Electron runtime install from `scripts/Build-And-Run-Automator.ps1`, `npm run package:win`), so the byte-locked asset keeps working as the repository's scripts change; keep them in step with that script. Editing the shipped asset needs a new template version once users may have installed it. Test it with `tests/update-and-restart-asset.spec.ps1`.
- Use the shared `ui/components/PathField.tsx` for Script Runner script paths, working directories, and template file/directory inputs. It supports typed/pasted paths, an app-owned Browse callback, and one dropped filesystem item resolved in preload through Electron `webUtils.getPathForFile`; it must never read dropped file contents.
- Keep path picker IPC limited to the active Script Runner tab and the allowlisted `file`/`directory` picker kinds. Native dialog options remain host controlled. Browser preview has no local filesystem and should show a recoverable path-resolution message for dropped items.
- The path field is a reusable UI component only. Do not migrate unrelated tabs or add a generic cross-tab file capability without updating their own contributor guides and authorization boundaries.

### Run lifecycle

- Start runs through `startScriptRun` in `ui/modules/scriptRunStore.ts`, never from component state, and dispatch through the bridge rather than the per-tab `services` object: `services` is disposed (cancelling in-flight actions) when the active tab changes, and the view unmounts when the compact window reopens on its home surface. Do not abort a run in an unmount cleanup.
- One run at a time. Output and history are memory-only (30 entries); never write them to storage, logs, or Run activity, which stays metadata-only. Explorer runs also start through `startScriptRun`, passing the `runExplorerAction` input as its override, so they get the banner and history; `recordExternalScriptRun` is only for results produced elsewhere.
- The backend cancels a module's requests when the compact window's service context ends (panel hides or tab changes). Run actions must be listed in `IsDetachedRunAction` in `src/Automator.Backend/BackendServer.cs` to outlive that. `runProfile`, `runAgain` and `runExplorerAction` are; add any new run action there.
- History rows show `describeRunError` for failed runs. It reads script error output and messages only from memory; do not log or persist it.

### Script authoring guidance

Write scripts to accept explicit arguments, use the configured working directory rather than assuming Automator's current directory, validate inputs, and exit promptly. Python scripts should write machine-readable JSON with the standard JSON library; PowerShell scripts should emit one JSON value in JSON mode; Bash scripts should use the configured Bash-compatible syntax and avoid interactive shell state. Test scripts should use isolated temporary files and clean them up.

Row removal uses `InlineConfirmButton` (`ui/components/InlineConfirmButton.tsx`). Keep the first button's existing accessible name, give the confirm button a distinct `Yes, …` name, and do not reintroduce `window.confirm` for row actions.

### Stale .fdb archive template — tests/fdb-stale-archive-asset.spec.ps1

**Steps**
